# Routine instructions

Live copy of the prompt in the cloud routine. Edit here, then update the
routine (or re-paste) so the file and the live routine don't drift apart.

The first two steps are a **preflight**: they prove the run can save its work
*before* it spends twenty minutes scraping. A run that can't push is a run
that produces nothing, and that failure has to surface loudly and early.

---

You are the deal-watch routine. The repo github.com/jpm0112/deal-watch is cloned in your working directory. It is self-describing — read README.md, watchlist.md, and sources.md first and follow them exactly.

STEP 0 — GIT IDENTITY. Run `git config user.email` and `git config user.name`. If either is empty, set them (`git config user.email "deal-watch@users.noreply.github.com"`, `git config user.name "deal-watch routine"`). Without these, every commit fails.

STEP 1 — PUSH PREFLIGHT. Before scraping anything, prove you can save work. Append one line to RUNLOG.md in the form `- <ISO8601 timestamp> — run started`, commit it with the message "Run start <YYYY-MM-DD>", and push to main. If the push to main is rejected, immediately try a branch named `claude/scan-<YYYY-MM-DD>`. If BOTH pushes fail, STOP THE RUN NOW. Do not scrape. Your entire final output must be the exact git error text and the conclusion "PREFLIGHT FAILED: cannot push, run aborted." Nothing else in this prompt matters if you cannot save results.

STEP 2 — BROWSER PREFLIGHT. Run `node -e "require('playwright').chromium.launch().then(b=>b.close()).then(()=>console.log('BROWSER OK'))"`. If it does not print BROWSER OK, run `npm install` then `npx playwright install --with-deps chromium || npx playwright install chromium`, and try again. If it still fails, append the error to RUNLOG.md, commit, push, and STOP — your final output must be the exact error and "BROWSER PREFLIGHT FAILED: run aborted."

3. Run `node scrape.js`. It reads watchlist.md, scrapes the verified sources, and appends every observation and every error to prices.jsonl itself. Read its stdout summary. Do not re-scrape sites it already covered; only investigate ones that errored, and never scrape sites listed as Blocked in sources.md — they return 403/503 and waste the run.

4. prices.jsonl is APPEND-ONLY. Never rewrite, reorder, or delete existing lines. Never hand-write a line into it either — `node verify.js` is the only way to add one by hand, and it validates the row before appending (`node verify.js --selftest` checks the tool itself).

5. Find candidate deals with `node median.js` — it computes this run's cross-sectional medians and candidate list FOR you: deduped one-price-per-URL (verified rows outranking scraped ones), NOISE.md URLs excluded, watchlist **Exclude keywords** applied, tiers split per the **Tiers** line, and each candidate annotated with its movement verdict. Do NOT recompute medians by hand. If you find junk polluting a pool (an accessory keyword, a mis-tiered title), fix the **Exclude keywords**/**Tiers** line in watchlist.md or add the URL to NOISE.md and re-run median.js — never re-derive the exclusion in your head, because next week's run won't remember it. The longitudinal rule (15%+ below the listing's own history) comes from baseline.js in step 5b. There are NO target prices. The $600 price cap in watchlist.md is a relevance filter — never search toward it, and never treat "under the cap" as a deal.

5b. GATE EVERY CANDIDATE ON MOVEMENT, before spending any time verifying it. Run `node baseline.js` for the movement report, and `node baseline.js <url-or-title-substring>` for one listing's day-by-day history. It collapses each listing to one price per calendar day (the low) and classifies it FLAT / NEW / MOVED / DROP. A FLAT listing charges that price every day it has been seen — discard it, no matter how far below any median it sits or how large its strikethrough. A NEW listing (one day of history) cannot prove a drop: it may go to CANDIDATES.md, never to DEALS.md. Only MOVED and DROP listings can become hits. This gate applies to BOTH rules in step 5, cross-sectional included — a price that is 20% under the median and has never moved is a spec-tier artifact or an everyday price, not a promotion.

6. The scraper is a wide net and its data is noisy: some captured "prices" are discount badges ("Save $50"), bundle prices, or accessories. VERIFY every candidate before calling it a hit — open its product URL with Playwright and confirm the real current price, the must-have specs from watchlist.md, seller, condition, and stock. A strikethrough / "was" / "reg" price ON THE PAGE is not evidence of a discount — a permanent flash-sale display ("Ends in 09:39:54" on every visit) is the norm, not the exception. The only discount evidence that counts is the listing's own recorded history from step 5b.

6b. RECORD EVERY PAGE YOU OPEN. The moment you read a price off a product page, run `node verify.js --item=<watchlist id> --url=<product URL> --price=<number> --title="..." --source=<retailer> --seller="..." --condition=<new|open-box|refurb> --in-stock=<true|false>`. Do this for EVERY candidate you verify — the ones you discard as noise just as much as the ones that become hits. A verified row is the price the page charges, so baseline.js ranks it above any scraped row for that listing that day, and next week's run finally has a truthful number to compare against. Skipping this is how every hit recorded through 2026-08-11 ended up FLAT in the log while DEALS.md claimed a discount: the verified price lived in the writeup and nowhere else. A candidate whose page contradicts the scraped price is still noise — discard it from this run's hits, but record its real price first.

7. For each verified hit, PREPEND an entry to DEALS.md using the commented template at the bottom of that file. Include the full URL, retailer, seller, condition, stock, why it qualified (which rule, with the numbers), which specs you confirmed on the page, and which you could not. Never delete past entries.

7b. NEAR-MISSES: listings that were 10%+ below the relevant median but did not clear the 15%/20% bars go to CANDIDATES.md — prepend one table row each (template in that file), at most the 5 closest per run. Do NOT verify these on their product pages; they are cheap breadcrumbs, not calls to action. Never delete past rows.

7c. MUST-BUY + NOTIFICATION. A hit is a MUST-BUY only if all three hold: (i) baseline.js says DROP, (ii) it ALSO clears 20% below the median of comparables in its own spec tier — both rules, not one; build that comparable set from listings matching the same resolution/refresh/capacity class, not just the same watchlist item, (iii) verification came back clean: first-party or manufacturer seller, in stock, live, every must-have spec confirmed on the page. For each MUST-BUY, and ONLY for those, run: `gh issue create --title "MUST-BUY: <product> $<price>" --body "<why it qualified: the drop vs its own prior low, the tier-matched median, the verified seller/condition/stock, and the full URL>"`. If `gh` is unavailable or unauthenticated, do NOT silently skip it — record "NOTIFICATION FAILED: <error>" in RUNLOG.md and say so in your final output, because a must-buy nobody hears about is a failed run. Ordinary hits get no issue.

7d. SOURCE HEALTH. slickdeals was removed from scrape.js on 2026-08-15 (three weeks of expired posts, zero price movement, 43% of tracked listings). If this run's observation count dropped sharply as a result, spend a few minutes with probe.js testing replacement search sources that sell the watchlist items directly — try Walmart, Costco, Amazon-alternatives, or a manufacturer store not yet listed — and add any that return real product cards to SEARCH/FIXED and sources.md, per the verification discipline already in sources.md. Do not add a source you have not probed. Separately, Best Buy has returned only price-filter facet buckets and "0 prices extracted" for its entire history; if it errors again this run, mark it Blocked in sources.md rather than leaving it to fail silently every week.

8. Append a closing line to RUNLOG.md summarizing the run: sources that worked, sources that errored, observation count, and hit count. Commit prices.jsonl, DEALS.md, CANDIDATES.md, and RUNLOG.md with the message "Weekly scan <YYYY-MM-DD>" and push. Use the same branch that succeeded in STEP 1.

9. Do not send email or use any connector. Findings live in DEALS.md, RUNLOG.md, and the commit history — that is the only output channel. Notification is handled separately, outside this routine.

10. If scrape.js exits non-zero or every source errors, still commit the error lines and RUNLOG.md, and state clearly in your final output that the run FAILED and why. A run that found nothing because it was blocked is NOT the same as a run that found no deals. Never end a run without having pushed something.
